# レンダリング文脈・キャッシュ

- テーマ/SEO プラグインは本番テンプレート描画の前にコンテンツを投機的にレンダリングしうる（抜粋生成・メタデータ解析）。「1リクエスト1回だけ出力」系のリクエストスコープ状態を真偽値で消費すると、破棄された投機的レンダリングが本番出力を潰す。再提示可能なシグネチャ（正規化属性+文脈post、またはpost ID単体）でクレームする（`Faq_List::claim_structured_data_slot()`、`Glossary_Term::claim_block_definition_slot()`）。また `wp_json_encode()` は不正 UTF-8 で false を返しうるため、シグネチャ・キー用途で `(string)` キャストしない（空文字衝突する）。
- ブロックテーマの `core/post-content` レンダリングは内部で `the_content` フィルターを適用するが `WP_Query::the_post()` を呼ばないため、`in_the_loop()` は常に `false` のままになる。本文レンダリングの前後にフックを挿入する等のリクエストスコープ検出ロジックを `in_the_loop()` に依存させるとブロックテーマでは一切発火しない。ブロックテーマ側は `pre_render_block`/`render_block_core/post-content` で対象ブロックのレンダリング開始・終了を深度カウンタで直接追跡する（`Template_Loader::fire_before_article_hook()`/`wrap_kb_article_content()`、`Glossary_Term::fire_after_definition_hook_for_block_theme()` が確立パターン）。
- `mbstring`/`intl` の両方が使えない前提のフォールバック実装は、主要ケースだけカバーすると漏れが出やすい（`Normalizer::normalize_fallback()` が全角ASCII変換のみで半角カナが素通りし、`fold_kana()`側にも半角カナの対応表が無かったため、五十音バケット判定で拾えない用語が発生した実績あり）。フォールバックを書く際は、拡張が使える経路が実際にカバーしている変換範囲（テストの入力パターン）を先に洗い出し、フォールバックが同じ範囲を満たすことを個別に確認する。
- サイト全体で共有するtransientキャッシュ（`WP_Query`の結果一式をキャッシュする`Llms_Index`/`Sidebar_Tree`/`Glossary_Index`系のクラス）は、`save_post_{type}`/`trashed_post`/`deleted_post` だけでは無効化経路が足りない。少なくとも次の3つを個別にフックする必要がある: (1) `wp_set_object_terms()`（管理画面のクイック編集での一括カテゴリー変更等）は`save_post`を経由せず`set_object_terms`アクションのみ発火する、(2) `update_post_meta()`の直接呼び出し（移行スクリプト等）も`save_post`を経由せず`updated_post_meta`のみ発火する（`deleted_post_meta`は第1引数が単一IDでなく配列である点に注意——コールバックの型宣言を`int`にすると`TypeError`になる）、(3) 新規インストールでの設定オプションの**初回**保存は、`update_option()`が`apply_filters("default_option_{$option}", false, $option, false) === $old_value`を満たす場合に内部で`add_option()`へ委譲するため、`update_option_{$option}`ではなく`add_option_{$option}`のみ発火する（WP core本体で実際に確認済み）。また、投稿本文のレンダリング結果を投稿ID単位でキャッシュする場合、本文が同期パターン（`core/block`）を参照していると`render_block_core_block()`が参照先`wp_block`投稿の現在のコンテンツを都度読み込むため、その`wp_block`投稿の編集はキャッシュ元の投稿自体を変更せず無効化フックが発火しない——`has_block( 'core/block', $post )`が真の場合はキャッシュ自体をスキップする。会員制プラグイン等が`pre_get_posts`で投稿取得を閲覧者の権限に応じて絞る環境、および多言語サイト（WPML/Polylang、`get_locale()`が言語ごとに変わる）では、サイト共通固定キーのキャッシュが特定の権限/言語の結果を他の閲覧者/言語へ漏洩させうる。前者は安価な識別手段が無く既知の限界として許容、後者は`get_locale()`をキャッシュキーへ折り込むことで解決できる（`Glossary_Index::cache_key()`が確立パターン）。
- 公開フック（`saai_autolink_dictionary`等、docs/DESIGN-HOOKS-API.mdで契約を明文化しているもの）の評価結果に依存する処理で、評価前に共有キャッシュ（`wp_cache_get`/transient）を先に参照する最適化は危険。そのフックが`$context`引数だけでなく任意のリクエスト状態（`is_user_logged_in()`等）に応じて出力を変えうる場合、`$context`をキャッシュキーへ折り込んでもキー化できない差異までは防げず、あるリクエストの結果を別のリクエストへ誤って共有しうる（`Autolinker::process()`で実際に2ラウンドのレビューを経て発覚し、順序変更自体を差し戻した実績）。このような処理は「フック評価→空/該当なし判定→キャッシュ参照」の順序を変えてはならない。
- パフォーマンス目的で`get_the_excerpt()`を`wp_trim_words( $post->post_content, ... )`直呼びに置き換えて`the_content`パイプラインを迂回すると、会員制・年齢制限プラグイン等が`the_content`フィルターで行う本文保護（保護コンテンツをティーザーへ差し替える等）も同時に迂回してしまう。公開・未認証のエンドポイント（REST検索結果等）で本文由来の抜粋を返す箇所では、性能より`the_content`を経由する`get_the_excerpt()`を常に優先する。
- `WP_Query` の `fields => 'ids'` は投稿キャッシュを温めないため、返った ID 一覧に `get_permalink()` / `get_the_title()` を回すと件数分の `get_post()` クエリになる（N+1）。ループ前に `_prime_post_caches( $ids, false, false )` で一括プライムする（WP 6.1 以降 private 扱いではなく WooCommerce 自身も使用。テストは「件数 1 と 3 でクエリ数が増えない」比較で固定する — `get_post()` はミス時に自分でキャッシュするので「プライム済みか」の assert はトートロジー）。ただしプライム（と `WP_Post::get_instance()`）は「存在しない」をキャッシュしないため、完全削除された ID が残りうる一覧（紐づけメタ等。ゴミ箱の自動削除で増える）ではその ID ごとに `get_post()` が DB へ行く。その場合は `get_posts( [ 'post__in' => $ids, 'orderby' => 'post__in', 'posts_per_page' => count( $ids ), … ] )` の 1 本で取得し公開判定も SQL に寄せる（`orderby` を省くと既定の `post_date DESC`、`posts_per_page` を省くと既定 `numberposts => 5` で 6 件目以降が黙って欠ける。どちらも「ID 順でも日付順でもない並び」と「6 件以上」のテストで固定する — `Export_Metadata::products()`）。
