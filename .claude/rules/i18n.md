# i18n（翻訳ファイル・テキストドメイン・文字数カウント）

- ブロックのJS（editorScript等）が翻訳対象文字列を含む場合、`wp_set_script_translations()` が実際に探す翻訳JSONのファイル名は、登録スクリプトの**ビルド後パス**（例: `build/faq-list/index.js`）から算出したMD5ハッシュに基づく。`wp i18n make-pot` が参照コメントに残す **src/ 側のパス**（例: `src/faq-list/index.js`）とは異なるため、`wp i18n make-json` には `--use-map='{"src/foo/index.js":"build/foo/index.js"}'` でビルド後パスへの対応付けを渡す必要がある。また `make-json` の `--purge` は変換元の `.po`/`.pot` から該当エントリを削除するため、PHPとJS双方で使う文字列（例: タクソノミーラベルとブロックのセレクトオプションで共用する「カテゴリー」）があると、次に `.po` から `.mo` を再生成した際にPHP側の翻訳が消える。`.po` をPHP/JS共通の単一ソースとして運用するなら `--no-purge` を使う（`bin/i18n-build.sh` が確立パターン）。
- `WP_Textdomain_Registry::get_paths_for_domain()` が探索するのは `WP_LANG_DIR/plugins`・`WP_LANG_DIR/themes`・`custom_paths`（`load_plugin_textdomain()`/`load_theme_textdomain()` が登録）の3つだけ（WP 6.9 / 7.1 の core 実装で確認済み）。つまり **`load_plugin_textdomain()` を呼ばないプラグインでは、`Domain Path` ヘッダーがあってもプラグイン自身の `languages/` は一切探索されない**。WordPress.org 配布プラグインは `load_plugin_textdomain()` の削除が審査の要求なので、同梱翻訳はそもそもロードされなくなる＝配布ZIPから `languages/` を外し `Domain Path` ヘッダーも消すのが整合的（無料版は Issue #61 でこの構成。翻訳は translate.wordpress.org の言語パックが `WP_LANG_DIR/plugins` へ配信される）。WooCommerce.com 配布の有料版は言語パック対象外なので `load_plugin_textdomain()` を維持する（`languages/` に `.pot` と ja の `.po`/`.mo`/`.l10n.php`/JSON を同梱し、`bin/i18n-build-woo.sh` で再生成する。`.po` は再生成後の `.pot` の差分を見て手で更新する。翻訳文字列を持つ JS を有料版の `src/` に足したら、同スクリプトの `--use-map` にもビルド後パスを足す——足さないと読まれない JSON が黙って生成される）。
- `load_plugin_textdomain()` を使う側（有料版）で効く2点。(1) **停止中**のプラグイン一覧画面の名前・説明は core の `_get_plugin_data_markup_translate()` が `init` を経由せず独自に `load_plugin_textdomain()` を呼ぶ経路で翻訳するため、`Domain Path` ヘッダーが無いとプラグイン直下しか探索されず同梱 `.mo` に到達しない。(2) 明示パスが `custom_paths` に載るので、`wp_set_script_translations()` 側でパスを省略してもJS翻訳が解決される（スクリプトごとの個別パス指定は不要）。
- `wp_trim_words( $text, $n )` の `$n` は常に「単語数」とは限らない。`wp_get_word_count_type()` が返す語（翻訳対象文字列）が `characters` で始まる言語（`ja` で実機確認済み。CJK言語全般が対象と推測）では「文字数」カウントに切り替わり、非CJKスクリプト（英語等）の文章を渡すと単語の途中で機械的に切り詰められる（例: 日本語ロケールのサイトで英語の抜粋を `wp_trim_words($text, 55)` すると「55文字」で切れる）。逆に `words` の言語では、空白の無い和文が1単語と数えられ、まったく短くならない。この数え方はフィルターでは変えられない: `WP_Locale::init()` が `word_count_type` を一度だけ保存し、`wp_get_word_count_type()` にはフィルターが無いので、gettext フィルターを後から足しても効かない（Issue #56 の当初の方針案はこれで動かなかった）。public プロパティの `$wp_locale->word_count_type` を書き換えれば変わるが、和文と英文の混ざった文章はどちらの数え方でも扱えない。用語の抜粋は `Plain_Excerpt::trim_words()` で文章の文字種から数える（和文などは1文字、英文などは1語を1単位）。テストで文字数モードを再現するには `$GLOBALS['wp_locale']->word_count_type` を書き換えて `finally` で戻す（tests サイトに ja の言語パックは要らない）。有料版 `Product_Sections::definition()` は未修正（無料版の内部クラスを呼べないため。Issue #89）。
