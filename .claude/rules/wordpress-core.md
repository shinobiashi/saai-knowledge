# WordPress core の挙動（フック・クエリ・メタ・REST・管理画面・ライフサイクル）

- `register_post_meta()` の `auth_callback` は WordPress が `auth_{$object_type}_meta_{$meta_key}` フィルタ経由で6引数（`$allowed, $meta_key, $object_id, $user_id, $cap, $caps`）を渡して呼び出す。シグネチャをこれに合わせる（PHPは超過引数を無視するため実害はないが契約を明確にする）。
- `register_activation_hook()` のコールバックは、プラグイン本体ファイルが `activate_plugin()` 内で（WordPress自身の `init` より後に）はじめて `include` される関係で、同一リクエスト内では通常の `init`/`plugins_loaded` フックがまだ発火しない。`activate()` で `flush_rewrite_rules()` する場合、CPT/タクソノミー登録を `init` に任せず、`activate()` 内で直接呼んでから flush する。
- サードパーティが実装しうる公開フィルター（`saai_*`）は契約と異なる型（非string等）を返す可能性がある前提で、`file_exists()` など型に敏感な組み込み関数へ渡す前に `is_string()` 等のガードを入れる（PHP 8+ はTypeErrorで即死するため）。
- `register_term_meta()` / `register_post_meta()` で `default` を設定すると、`get_term_meta()` 等は meta 行が無くても default を返すため「未設定」と「明示的な default 値」を区別できない。UI で未設定を空欄表示する場合や行の有無で分岐する場合は `metadata_exists()` で判定する。未設定に default を表示すると、フォーム保存の往復で不要な meta 行が実体化する（saai_order の編集フォームと一覧列で2回指摘された実績あり）。
- `WP_Term_Query` の `orderby` は文字列のみ対応（配列 orderby は `WP_Query` のみ）。core の `parse_orderby()` が値を直接 `strtolower()` に渡すため、配列を渡すと PHP 8+ では `terms_clauses` フィルター到達前に TypeError になる。
- 優先度リストを `array_flip()` して `usort()` で並べ替える際、同一優先度の候補が2つ以上あると比較関数が `0` を返し、PHPの `usort()` は不安定ソートのため勝者がリクエストごとに不定になりうる（`plugin_taxonomy_template_wins()` のタクソノミーテンプレート優先度判定で実際に発生）。同点時のタイブレーカー（例: 自プラグイン由来かどうか）を明示的に用意する。
- 自身が登録しているフィルターを、内部API呼び出し中の自己干渉回避のため一時的に `remove_filter()` する場合、無条件の remove→add ではなく `has_filter()` で事前登録状態を記録し、元々登録されていた場合のみ `add_filter()` で復元する。`register()` を経由せず直接呼ばれる経路（reflectionを使うテスト等）では、無条件の復元がフィルターをプロセスの残り期間グローバルに登録したままにする副作用を生む。
- `get_the_title()` は the_title フィルターにより HTML 文字参照（`&#038;`、`&#8217;` 等）を含む文字列を返す。HTML へは `esc_html()` でそのまま出してよい（`_wp_specialchars` は `double_encode=false` で既存エンティティを再エンコードしない。「esc_html で二重エンコードされる」というレビュー指摘は誤検知）。JSON-LD などプレーンテキスト先へは `wp_strip_all_tags()` の後に `html_entity_decode()` が必要。順序は逆にしない（先にデコードすると、本文に文字として書かれた `&lt;br&gt;` がタグとして消える）。文字数・語数を数えて切り詰めるのはデコードした後のテキストで行い、デコードは1回だけにする（デコード前に数えると `&nbsp;` でつながった語が1語になり、切り詰めた後にもう一度デコードすると `&amp;lt;` が `<` になる。`Plain_Excerpt::trim_words()`、PR #91 G1-2）。`the_content` の出力も wptexturize が `'` `"` を `&#8217;` などに変えるので同じ扱いにする。ターム名（`$term->name`）も保存時の `_wp_specialchars` で `Q&amp;A` になっているので、プレーンテキスト先へは同じく strip → decode する（`Breadcrumbs::json_ld()` で漏れていた、#90）。ただし出力先が Markdown ならデコードしない（CommonMark では文字参照がそのまま文字を表すため。`Markdown_Converter::to_plain_text()` と `fallback_plain_text()` の違い）。また `is_admin()` が偽のときは `protected_title_format` / `private_title_format` を適用して「保護中: 」「非公開: 」を前置する——**REST リクエストは `is_admin()` が偽**なので REST 経由のタイトルには接頭辞が付く。加えて**パスワード保護された投稿の `post_status` は `publish` のまま**なので、接頭辞を取り除く実装にするなら保護状態を別フィールドで伝えないと、その情報が UI から完全に失われる。
- the_content フィルターを通さず本文を手動レンダリングする場合は core の順序を再現する: classic コンテンツは `WP_Embed::run_shortcode()`→`autoembed()`（priority 8 相当、wpautop 前）→wptexturize→wpautop→shortcode_unautop→do_shortcode→`wp_filter_content_tags()`（priority 12 相当）。`setup_postdata()`（実体は `WP_Query::setup_postdata()`）は `$id`, `$authordata`, `$currentday`, `$currentmonth`, `$page`, `$pages`, `$multipage`, `$more`, `$numpages` の9個のグローバルを変更するが、`$GLOBALS['post']` 自体は代入しない（それを行うのは `WP_Query::the_post()` 側の `$post = $this->next_post();` のみ）。そのため、通常の Loop の外（REST/管理画面のバッチ処理等）で特定の投稿を「現在の投稿」として扱いたい場合は、`setup_postdata( $post )` を呼ぶ前に自分で `$GLOBALS['post'] = $post;` も代入する必要がある——省略すると、本文中の `get_post()`（引数なし）を呼ぶショートコード/動的ブロックが別の投稿（前のリクエストの残留値や別のバッチ対象）を返してしまう（`Faq_List::render_answer()` は当初から対応済みだったが、`Markdown_Output::render()` と `Export::build_record()` はこの代入を欠いており、Codexレビューで指摘され修正した実績がある）。復元は（`$post` を含めた）スナップショット方式で行う（直前の global post が null のケースは `setup_postdata()` では戻せない）。直前の投稿が `WP_Post` なら、先に `setup_postdata( 直前の投稿 )` をかけ直して `the_post` を再発火し、そのあとでスナップショットを書き戻す。書き戻しは内側の `finally` に置き、`the_post` のコールバックが例外を投げても飛ばされないようにする。`the_post` を起点に状態を持つサードパーティ（WooCommerce の `$product` 等）は、代入だけでは戻らないため。`wp_reset_postdata()` も `reset_postdata()`→`setup_postdata()` で `the_post` を再発火するが、戻り先はメインクエリの投稿なので Query Loop 内では使えない（`Faq_List::render_answer_uncached()` が確立パターン。`Markdown_Output`/`Export` は独立リクエストで完結するため未適用）。
- Site Editor でカスタマイズされたプラグイン登録テンプレートは `WP_Block_Template::$plugin` を保持したまま `$source` が `'custom'` の wp_template 投稿になる。「未変更の同梱テンプレートが描画されるか」の判定は `$plugin` だけでなく `'plugin' === $source` も見る（カスタマイズ版は本物のページネーション等を持ちうる）。
- `saai_template` のように「template_redirect のコールバックから登録されうる」と文書化された公開フィルターの評価結果に依存する自前の template_redirect コールバックは `PHP_INT_MAX` で登録する。プラグイン本体のフック登録はアドオンの template_redirect コールバック登録より必ず先に走るため、既定優先度では相手の登録前に判定してしまう。
- WordPress の `WP_Hook` は同一 priority のコールバックを登録順で実行するため、`PHP_INT_MAX` だけでは「最後に実行される」ことを保証しない。テーマの `functions.php` は `plugins_loaded`（プラグイン本体のフック登録タイミング）より後に読み込まれるため、同じ `PHP_INT_MAX` で登録すればテーマ側が後から実行される。「確実に最後の値を捕捉したい」`the_content`/`the_title` 系フックは `plugins_loaded` ではなく `wp` アクションから登録する。`WP_UnitTestCase::go_to()` は（`WP::main()` 経由で）`wp` を発火させるが、`template_redirect`（本番の `template-loader.php` でのみ発火）はテスト環境では発火しないため、`wp` を使うと既存テストで動作を検証し続けられる。
- `WP_Block::render()`（wp-includes/class-wp-block.php）は子ブロックを完全にレンダーしてから自身のフィルター（汎用 `render_block` → 動的 `render_block_{$name}` の順）を適用する。子ブロックのフィルターで値を捕捉しても、祖先ブロック（Group やアクセス制御ブロック等）が自身の後続フィルターでその値を破棄・書き換えできてしまう。生存確認は祖先自身の動的フィルターへ一回限りの自己削除コールバックを動的登録して逆算する（祖先のブロック名は子の捕捉時点では未知なので、汎用 `render_block` フィルターで祖先のブロック名を受け取ってから登録する）。また、ブロックキャッシュプラグインが対象ブロック自体ではなくその祖先単位で `pre_render_block` を短絡すると、子サブツリーの処理が一切発生せず、ブロック境界情報が失われたキャッシュ済みHTML文字列からは目的のテキストを信頼できる方法で抽出できない（既知の制約として許容し、値を出力しないに留める）。
- `doing_filter( 'the_content' )` / `doing_filter( 'get_the_excerpt' )` は、コンテンツ処理中の再入呼び出し（回答内のショートコードが同じ投稿の `get_the_title()` や `the_content` を再度呼ぶ等）を確実に検出できる。捕捉ロジックが「本物の一次レンダーか、コンテンツ内部からの再入呼び出しか」を区別する必要がある場合のガードに使う。ただし `doing_filter()`/`current_filter()` はフィルター名がスタック上に存在するか（`current_filter()` は最内側のみ）を見るだけで、ネスト順序も「特定の関数が実際に実行中か」も証明しない——同一優先度の別コールバックや優先度前後のブラケット登録でも容易に誤検知する（`Autolinker::process()` の `wp_trim_excerpt()` 検出で複数回再発）。特定の関数が呼び出しスタック上に実在するかを確実に判定したい場合は `debug_backtrace()` で関数名を直接照合する（`is_inside_wp_trim_excerpt()` が実例）。コストを避けるため、まず該当フィルターの `doing_filter()` で安価に足切りしてから呼ぶ。
- 再入防止フラグは、副作用を持つ処理全体の入口（例: 公開APIの冒頭）で短絡する必要がある。内部のデータ取得ステップだけを安全な空値に差し替えても、その後に適用される公開フィルター（`saai_autolink_dictionary` 等）がその空値を独自データで置き換えられるため、再入呼び出しに副作用が残りうる（`Autolinker::process()`/`building_dictionary` で実例）。
- `core/post-title` の `render_block_core_post_title()`（wp-includes/blocks/post-title.php）は `get_the_title()` を意図的に引数なし（グローバル `$post` 依存）で呼ぶ。`$block->context['postId']` は存在チェックと `isLink` 時のパーマリンク生成にのみ使われ、表示するタイトルテキスト自体には使われない — `core/post-content` の `get_the_content()` と同じ設計。
- PHPのPCRE `\p{Han}`/`\p{Katakana}`/`\p{Hiragana}`（bare形式のUnicodeプロパティ）は、実装によっては各文字の Script ではなく Script_Extensions を参照するため、複数スクリプトで共有される句読点（例: `。` U+3002）が Han・Hiragana・Katakana すべてにマッチしてしまう（実機検証で確認: `preg_match('/\p{Han}/u','。')` が `1` を返す）。スクリプト単位の文字種判定が必要な場合は `\p{Script=Han}` のような明示的構文を使う（`Autolinker::char_class()` で実例）。
- `register_rest_route()` の `args` に `minimum`/`maximum` 等のスキーマ制約を書いても、`validate_callback` を明示的に `rest_validate_request_arg` にしない限り自動検証されない（out-of-range値が黙って通る）。なお `WP_REST_Server::dispatch()` は `has_valid_params()` を `sanitize_params()` **より先に**実行するため、明示した `minimum`/`maximum` は `sanitize_callback` より先に働く（`absint` 等が負値を正値へ化かす前に 400 になる）。また `array( 'callback' => ..., 'schema' => ... )` 形式以外（複数メソッドの配列など）で登録する場合、`schema` は各メソッド定義の兄弟オプションとして置く必要がある——`callback` と同じ配列の内側に置くと `WP_REST_Server::get_data_for_route()` がOPTIONS discoveryで拾えない。
- シングルトンサービスの結果メモ化（例: 高コストなフィルター呼び出しの結果キャッシュ）は、Swoole/FrankenPHP/WP-CLI等の永続ワーカーではインスタンスがリクエストをまたいで生存するため、キャッシュのクリアをリクエスト境界（例: REST `callback` の `finally` ブロック）で明示的に行う。クリアし忘れると最初のリクエストのスナップショットが以後のリクエストへ漏れ続ける。
- WordPress の管理メニューで、複数の CPT + 独自トップレベルページを1つの親メニューに集約する場合（`show_in_menu` に親スラッグを指定）、`wp-admin/menu.php` は CPT のサブメニュー項目を `admin_menu` アクション発火前に挿入し、`wp-admin/menu-header.php` はトップレベルリンクの遷移先を常に `$submenu[$parent][0]` にする。`add_submenu_page()` で「設定」項目を追加するだけでは末尾に追加されるだけなので、トップレベルリンクを独自ページに向けたい場合は追加後に `$submenu[$parent]` を直接操作して先頭へ並べ替える必要がある（`Settings::register_menu()` で実例）。
- `register_setting()` の `sanitize_callback` は `sanitize_option_{$option}` フィルターとして登録され、対象オプションへのあらゆる `update_option()` 呼び出し（設定画面からの保存に限らない。既存テストの部分的な `update_option()` 呼び出しも含む）に適用される。フロントエンドでも `saai_default_settings` のようなフィルター済みデフォルトを `get_option()` に反映させたいだけなら、`register_setting()` 自体を無条件実行にするのではなく、`default_option_{$option}` フィルターだけを（`sanitize_callback` を伴わずに）無条件登録する方が安全（`Settings::filter_default_option()` で実例。前者を試して既存テストが壊れた実績あり）。
- PHP 8 は内部関数（`boolval` 等の組み込み関数）に宣言以上の引数を渡すと `ArgumentCountError` で即死する一方、ユーザー定義関数・クロージャは超過引数を黙って無視する。プラグインの拡張フックが外部提供のコールバック（`'sanitize' => 'boolval'` 等）を受け取り得る設計では、固定個数の引数で無条件に `call_user_func()` せず、`ReflectionFunction`/`ReflectionMethod::getNumberOfParameters()` でコールバックの実引数個数を確認してから渡す（`Settings::call_field_sanitizer()` で実例）。
- `uninstall.php` はプラグイン本体のオートローダーを経由しないため、直接 `require` したクラスがさらに参照する別クラス（例: `Post_Types::shared_args()` が `Settings::PAGE_SLUG` を参照）も個別に `require` する必要がある。この種の欠落はPHPUnitテストでは検知できない（テストプロセスは既にプラグイン本体のオートローダー経由で全クラスが読み込まれた状態で走るため）。検証するには実際にプラグインを deactivate した状態で `define('WP_UNINSTALL_PLUGIN', true); require 'uninstall.php';` を別プロセスで実行する。
- 投稿の削除に連動して transient/キャッシュを無効化するフックは `save_post_{type}` / `trashed_post` だけでは不十分。`wp_delete_post( $id, true )`（REST APIの `force=true`、`wp post delete --force`）は `wp_trash_post()` を経由しないため `trashed_post` が発火せず、`deleted_post` も必ず併用する（`Autolinker::handle_post_deleted()` が確立パターン）。
- 自プラグインが一時的に他のフック（`redirect_canonical` 等、自分が登録していないもの）を `remove_filter()` する場合、優先度を省略すると既定値10でしかマッチしない。core/他プラグインがそのフックを異なる優先度で登録している可能性を考慮し、`has_filter()` で実際の登録優先度（`false` の場合は未登録）を取得してから明示的に指定して `remove_filter()` する。
- `Plugin_Upgrader::upgrade()`/`bulk_upgrade()` によるWordPress.org自動更新は `register_activation_hook()` のコールバックを発火しない。新バージョンで rewrite rule や新規 option を追加する場合、`activate()` だけに頼ると既存インストールでは反映されないままになるため、`init` でプラグインのバージョン文字列を保存済みオプションと比較し、不一致なら一度だけ `flush_rewrite_rules()` 等を実行する経路を別途用意する。
- マルチサイトのネットワーク管理画面（Network Admin）は `admin_notices` ではなく `network_admin_notices` を発火する。両方の画面で通知を出したい場合は `all_admin_notices` フックを使う（`saai-knowledge-for-woocommerce` の `Bootstrap::register_notice()` で実例。Codexレビューで指摘）。
- ショートコードの真偽値属性を `rest_sanitize_boolean()` で解釈すると `"false"` / `"0"` 以外（`no` / `off`）が真になる。`filter_var( $value, FILTER_VALIDATE_BOOLEAN, FILTER_NULL_ON_FAILURE )` を使う。ただし空文字はこれでも `false` になるので、未指定扱いにするなら先に分岐する（有料版 `Shortcodes`）。
- `WP_Query` の `posts_per_page` は SQL の `LIMIT` になるため、**クエリ後に `current_user_can()` で件数を絞る実装は「打ち切られた1ページ」を対象にする**ことになり、条件を満たす投稿が存在しても空や要求件数未満を返しうる。権限による絞り込みはクエリ段階へ入れる（`perm => 'editable'` は `edit_others_posts` を持たないユーザーに `post_author = <user>` を WHERE へ追加する）。ただし **`post_status => 'any'` のままだと `perm` は一切効かない**——core の `'any'` 分岐は「このステータスではない」という除外条件しか組み立てず `$r_status` が空のままなので、`perm` を適用する分岐に到達しない（`class-wp-query.php`）。`array( 'publish', 'future', 'draft', 'pending', 'private' )` のように明示して初めて効く。
- `register_post_meta()` の `single => false` + `show_in_rest => true` は REST に配列として出て書き込みは全行置換になるが、これは **CPT が `custom-fields` を supports している場合のみ**（`WP_REST_Posts_Controller` は supports が無いと `meta` をスキーマから外す）。無料版の CPT 定義から外すと有料版のエディターパネルが無言で保存しなくなる類の跨プラグイン契約なので、依存する側にテストを置く。また `wp_postmeta` に (post_id, meta_key, meta_value) の一意制約は無く `add_post_meta()` の `$unique` は meta_key 単位でしか効かないため、多値メタの「1値1行」は**保存形式の規約**であって行の一意性保証にはできない（同時書き込みで重複しうる前提で、読み取り側を `array_unique` / `GROUP BY` で畳む）。
