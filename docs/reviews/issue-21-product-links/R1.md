## 指摘

### [R1-1][High][includes/class-links-controller.php:311 / assets/js/linked-products-panel.js:223]

「追加」の主動線が壊れている。サーバーは `'s' => ...` で**タイトル・本文・抜粋の全文検索**をするが、
`ComboboxControl` は返ってきた options を**クライアント側で `option.label`（=タイトル）への部分一致で
再フィルター**する。本文だけが一致する投稿が `per_page` 枠を食い潰すとタイトル一致の項目がレスポンスに
入らず、入っていても本文一致分は全部クライアント側で消えるため、**ドロップダウンが空になる**。
DESIGN.md §6.1 は当ルートを「タイトル検索」と規定しているので仕様違反でもある。

**再現/根拠:** core 実装を確認済み — `wp-includes/js/dist/components.js:38479` が
`normalizeTextString( option.label ).indexOf( match )` で絞る。サブエージェントが wp-env 実機で
本文のみ一致21件 + タイトル一致1件を用意し、`per_page=20` でタイトル一致0/20・目的の1件が欠落することを再現。
`search_columns => array( 'post_title' )` で解決することを自分でも実測（本文のみ一致の投稿が除外された）。

**修正方針:** `WP_Query` と `/wp/v2/product` の両方に `search_columns` でタイトルのみを指定する。

### [R1-2][Medium][includes/class-links-controller.php:185-219]

商品側ルートの `edit_post( $product )` は**実効的な権限境界になっていない**。商品権限を持たない Author が
core REST の `/wp/v2/saai_faq/{自分のID}` へ `meta.saai_linked_products=[任意の商品ID]` を直接書けるため
（サブエージェントが実機で 200 / 保存成功を確認）、M5-3 で任意の商品ページに自分のコンテンツを載せられる。
これは「本命の認可はコンテンツ側 `edit_post`」という設計どおりの帰結だが、DESIGN.md からは読み取れず、
後続マイルストーンが誤った前提を置く危険がある。

**修正方針:** 設計意図どおりなので実装は変えず、DESIGN.md と permission_callback の docblock に
「商品側の cap は UI 到達性のみを制御し、実効境界はコンテンツ側 `edit_post`」と明記する。
（`edit_products` を要求する案は、Editor が商品を検索できるようにするために core REST を選んだ
本 PR の設計判断と正面から矛盾するため採らない。）

### [R1-3][Medium][includes/class-links-controller.php:367-376]

`visible_items()` の `read_post` 再チェック（情報開示ガード）が**テストで一切検証されていない**。
DELETE ルートの「コンテンツへの `edit_post` なしで 403」、`edit_link` が権限なしで空になることも未検証。

**再現/根拠:** ミューテーションテストで実証済み。`visible_items()` の本体を
`return array_values( $post_ids );`（フィルタ完全削除）に置換しても `Test_Woo_*` 55件が全部 PASS した。

**修正方針:** 他ユーザーの下書きが一覧・検索から落ちること、DELETE の権限、`edit_link` の空文字を検証する
テストを追加する。

### [R1-4][Medium][includes/class-links-controller.php:334-355]

商品メタボックスの1描画で `fields => 'ids'` の `WP_Query` を2本投げるため投稿キャッシュが温まらず、
`visible_items()` の `read_post` と `content_item()` の `get_the_title()` / `get_post_status()` /
`get_edit_post_link()` が**1件ごとに `get_post()` を発火**する（N+1）。

**修正方針:** ID 確定後に `_prime_post_caches()` を1回呼ぶ。件数上限は導入しない（管理UIで黙って
リンクを隠す方が有害。backlog の release-1.0.0-hardening R1-X1 で同種のキャップが回帰を生んだ実績がある）。

### [R1-5][Medium][assets/js/linked-products-panel.js:216-250]

パネルの商品／カテゴリー検索に**デバウンスが無く**、1キーストロークごとに REST リクエストが飛ぶ。
商品メタボックス側は 300ms デバウンス済みで実装が不揃い。

**修正方針:** `wp.compose.useDebounce` で 300ms に揃える。

### [R1-6][Medium][assets/js/linked-products-panel.js:112-130]

`useRecordsByIds()` は `/wp/v2/product` を既定（`status=publish`）で引くため、**下書き商品**に紐づくと
「Not found (#ID)」と表示され、実在する商品について嘘をつく。商品メタボックスからは下書き商品でも
紐づけられるので到達可能な経路。

**修正方針:** ラベルを「一覧に出せません（非公開・削除済みの可能性）」相当の正確な文言へ変える。
非公開ステータスまで引く対応は core posts controller が `edit_products` を要求し Editor で 400 になるため、
フォールバック分岐が必要で本ラウンドの範囲を超える → backlog。
